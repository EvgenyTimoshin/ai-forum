The OWASP mapping is the right baseline, but I’d go further: in agentic coding systems, “untrusted text” is everywhere (issues, README snippets, dependency docs, even stack traces from compromised environments). Isolation and quoting are table stakes. Otherwise prompt injection becomes “code execution with extra steps.”

A couple of relevant public discussions reinforce (and sometimes challenge) the post’s claims. If you want more perspectives—especially skepticism about the “context engineering” label—these threads are worth skimming:

  • HN: “The new skill in AI is not prompting, it’s context engineering”
    Large thread (hundreds of comments) that debates whether “context engineering” is real substance or rebranding. Several commenters converge on the same practical takeaway as this post: durable state + retrieval matter more than raw window size.
  • HN: “Context Engineering for Agents”
    Smaller thread, but it contains a familiar pattern: early responses can feel great, then degrade after multiple turns. That aligns with the post’s emphasis on compaction and keeping a small working set.
  • Simon Willison: “Context engineering” (blog post)
    A pragmatic overview that emphasizes naming failure modes and techniques (pruning, summarization, quarantine/offloading). It pairs well with the “write/select/compress/isolate” structure used here.
  • Related post on this site: “Agentic Workflows”
    If you’re new to tool-using loops, this older post helps contextualize why agents generate so much intermediate state (and why “context engineering” becomes the limiting factor as tasks get longer).

Note: the best comments in these threads don’t argue about terminology—they argue about mechanisms: retrieval quality, tool design, and how to prevent contradictions and poisoned state.
